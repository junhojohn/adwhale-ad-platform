# 광고 통계 대시보드 — 기능 정의 & API 스펙 (v0.2)

> 상태: **v0.2 — 필레이트 포함 결정, API 위치 `ad-dashboard-api` 결정**. 확정되면 5-4a → 5-4b 순으로 구현.
> 범위: 연습용 1차 버전. 지금 가진 데이터(`ad_stats_hourly`)로 만들 수 있는 것만 넣는다.

---

## 1. 목적 / 사용자

| 항목 | 내용 |
|---|---|
| 사용자 | 광고 운영자 (지금은 나 혼자) |
| 목적 | 광고·지면별 성과(요청/노출/클릭/CTR)를 기간별로 확인하고, 이상 징후(노출 급감, CTR 급변)를 빨리 발견 |
| 데이터 지연 | 최대 약 5분 (집계 배치 주기). 화면에 "데이터 기준 시각" 표시 |
| 시간대 | KST 고정 |

## 2. 사용할 수 있는 데이터

| 테이블 | 단위(1행) | 컬럼 | 상태 |
|---|---|---|---|
| `ad_stats_hourly` | 시간 × 광고 × 지면 | `requests`(광고가 응답된 요청), `impressions`, `clicks` | 있음 |
| `placement_stats_hourly` | 시간 × 지면 | `requests`(노필 포함 전체 요청), `filled`(광고 응답된 요청) | **5-4a에서 추가** |

필레이트는 "광고와 상관없는 지면 단위 지표"라서 광고별 테이블에 넣지 않고 지면별 테이블을 따로 둔다.
(노필 요청은 `ad_id`가 없으므로 광고별 테이블의 PK `(stat_hour, ad_id, placement_id)`에 들어갈 수 없음)

**노필 데이터 만들기 (5-4a)**: 지금 ad-api는 항상 광고 A001을 응답해서 필레이트가 늘 100%.
→ 더미로 **요청의 10%는 노필**(HTTP 204, 요청 이벤트 `adId = null`)로 응답하게 바꾼다.

**지금은 없는 데이터** (→ 1차 범위에서 제외, "향후" 참고)
- 매출/비용(eCPM, CPC 등): 단가·과금 데이터 없음
- 광고 이름·캠페인·광고주: 광고 마스터 테이블 없음 → ID로만 표시

## 3. 지표 정의

| 지표 | 정의 | 0으로 나누기 |
|---|---|---|
| 전체 요청 수 | `placement_stats_hourly.requests` 합 (노필 포함) | - |
| 필레이트 (%) | `광고 응답된 요청(filled) / 전체 요청 × 100` | 요청 0이면 `null` |
| 광고 요청 수 | `ad_stats_hourly.requests` 합 (= 광고가 응답된 요청) | - |
| 노출 수 | `SUM(impressions)` | - |
| 클릭 수 | `SUM(clicks)` | - |
| CTR (%) | `클릭 / 노출 × 100`, 소수 2자리 | 노출 0이면 `null` ("-" 표시) |
| 노출률 (%) | `노출 / 광고 요청 수 × 100`, 소수 2자리 (광고를 받았는데 실제로 보여진 비율) | 요청 0이면 `null` |

> **광고 필터를 걸면 필레이트·전체 요청 수는 표시하지 않는다** (`null`).
> 노필 요청은 어떤 광고에도 속하지 않기 때문. 지면 필터만 걸었을 때는 그 지면의 필레이트를 보여준다.

> 비율 지표는 **합계끼리 나눈다** (시간별 CTR의 평균 ✘). 예: 10시 1/10, 11시 9/90 → CTR = 10/100 = 10%

## 4. 화면 구성 (1페이지)

```
┌──────────────────────────────────────────────────────────────────────┐
│ 기간 [오늘|어제|최근 7일|직접 선택]  광고 [전체 ▾]  지면 [전체 ▾]       │ ← A. 필터
│                                        데이터 기준: 2026-10-07 15:25 │
├────────────┬────────────┬────────────┬────────────┬──────────────────┤
│ 요청 13,700 │ 필레이트 90.07% │ 노출 10,120 │ 클릭 312 │ CTR 3.08% │ 노출률 82.01% │ ← B. KPI 카드
├────────────┴────────────┴────────────┴────────────┴──────────────────┤
│  ▇ 노출  ▇ 클릭   ─ CTR                                              │ ← C. 추이 차트
│  (기간 1일 이하: 시간별 / 2일 이상: 일별)                              │
├──────────────────────────────────────────────────────────────────────┤
│ 광고  │ 지면 │ 요청 │ 노출 │ 클릭 │ CTR │ 노출률   (컬럼 클릭 시 정렬)  │ ← D. 상세 테이블
└──────────────────────────────────────────────────────────────────────┘
```

| 영역 | 기능 | 사용하는 API |
|---|---|---|
| A. 필터 | 기간(최대 31일), 광고/지면 선택. 바꾸면 B·C·D 모두 갱신 | `GET /v1/stats/filters` |
| B. KPI 카드 | 선택 조건의 합계 지표 6개 (광고 필터 시 요청·필레이트는 "-") | `GET /v1/stats/summary` |
| C. 추이 차트 | 시간별 또는 일별 노출·클릭(막대) + CTR(선) | `GET /v1/stats/timeseries` |
| D. 상세 테이블 | 광고 × 지면별 합계 | `GET /v1/stats/breakdown` |

## 5. 비기능 요구사항

| 항목 | 목표 |
|---|---|
| 응답 시간 | 각 API 300ms 이내 (최대 31일 범위 기준) |
| 조회 범위 | 최대 31일 — 넘으면 400 |
| 인증 | 1차 범위 제외 (로컬 전용). 실무에선 사내 로그인 필수 |
| 캐시 | 1차는 MySQL 직접 조회. 느려지면 Redis 캐시 추가 (5-5 후보) |

## 6. API 스펙

공통
- 기준 URL: `http://localhost:8090` (대시보드 전용 API, SDK용 ad-api와 분리 — 아래 7번 참고)
- 날짜 파라미터: `from`, `to` = `yyyy-MM-dd` (KST, **양 끝 포함**). 예: `from=2026-10-01&to=2026-10-07` = 7일
- 선택 필터: `adId`, `placementId` (없으면 전체)
- 에러: `400` `{ "error": "INVALID_PARAM", "message": "..." }`
  - `from > to`, 범위 31일 초과, 날짜 형식 오류, 허용되지 않은 `granularity`/`by`

### 6-1. `GET /v1/stats/filters` — 필터 선택지
```json
{ "adIds": ["A001", "A002"], "placementIds": ["P01", "P02"] }
```
최근 31일 안에 데이터가 있는 광고/지면 목록.

### 6-2. `GET /v1/stats/summary?from&to[&adId][&placementId]` — KPI 카드
```json
{
  "from": "2026-10-01", "to": "2026-10-07",
  "totalRequests": 13700, "filledRequests": 12340, "fillRate": 90.07,
  "impressions": 10120, "clicks": 312,
  "ctr": 3.08, "impressionRate": 82.01,
  "dataUpdatedAt": "2026-10-07T15:25:03"
}
```
- `dataUpdatedAt` = 조회 범위 안 `updated_at`의 최댓값 (데이터 없으면 `null`)
- `adId`를 지정하면 `totalRequests`, `fillRate`는 `null`

### 6-3. `GET /v1/stats/timeseries?from&to&granularity=hour|day[&adId][&placementId]` — 추이 차트
```json
{
  "granularity": "hour",
  "points": [
    { "time": "2026-10-07T14:00:00", "totalRequests": 133, "fillRate": 90.23, "impressions": 98, "clicks": 3, "ctr": 3.06 },
    { "time": "2026-10-07T15:00:00", "totalRequests": 0,   "fillRate": null,  "impressions": 0,  "clicks": 0, "ctr": null }
  ]
}
```
- **데이터가 없는 시간/날짜도 0으로 채워서** 반환 (차트에 빈 구간이 끊기지 않게)
- `granularity=hour`는 최대 2일까지만 허용 (점이 너무 많아짐)

### 6-4. `GET /v1/stats/breakdown?from&to&by=ad|placement|ad_placement[&adId][&placementId]` — 상세 테이블
```json
{
  "by": "ad_placement",
  "rows": [
    { "adId": "A001", "placementId": "P01", "requests": 8000, "impressions": 6500, "clicks": 210, "ctr": 3.23, "impressionRate": 81.25 }
  ]
}
```
- `by=placement`일 때만 각 행에 `totalRequests`, `fillRate` 포함
기본 정렬: 노출 수 내림차순. (화면의 컬럼 정렬은 프론트에서 처리)

## 7. 구현 위치 결정 (제안)

| 안 | 내용 | 장단점 |
|---|---|---|
| **A. 새 모듈 `ad-dashboard-api` (:8090)** ← **결정** | 대시보드 전용 API 앱 | SDK 트래픽(초당 수천)과 내부 조회 트래픽 분리. 대시보드 API가 느려도 광고 서빙에 영향 없음. 인증 정책도 따로 |
| B. 기존 `ad-api`에 추가 | `/v1/stats/*`를 ad-api에 | 앱 수가 적음. 대신 ad-api가 MySQL 의존성까지 갖게 되고, 무거운 통계 조회가 광고 응답 속도에 영향 |
